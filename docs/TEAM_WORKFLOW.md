# Як ми працюємо разом — P1t0n

Коротко: **код і документи — в одному репозиторії GitHub, великі сирі дані — у спільній теці Google Drive, розмови — в одному чаті, задачі — на одній дошці.** Нічого важливого не живе лише на чиємусь ноутбуці.

## 1. Інструменти

| Для чого | Чим | Правило |
|---|---|---|
| Код, контекст-файл, документи, малі файли даних | Репозиторій GitHub `p1t0n` (публічний) | Єдине джерело правди. Якщо цього немає в `main` — цього не існує |
| Сирі CSV із FIRMS, великі проміжні файли | Спільна тека Google Drive | У git не кладемо файли понад ~20 МБ |
| Задачі | GitHub Issues + дошка Projects (To do / Doing / Review / Done) | Одна задача — одна людина — одна гілка |
| Швидкі питання | Один чат команди (Telegram або Discord) | Рішення, прийняті в чаті, дублюємо в Issue або в `CLAUDE.md` |
| Тексти для форми, сценарій відео | `docs/` у репозиторії | Чернетки можна в Google Docs, фінал — у `docs/` |
| Слайди, відео | Google Slides / Drive, доступ «усі, хто має посилання» | Посилання записати в `docs/SUBMISSION_CHECKLIST.md` |

## 2. Перший запуск для кожного учасника

1. Прийняти запрошення до репозиторію на GitHub.
2. Склонувати: `git clone https://github.com/<власник>/p1t0n.git`
3. Відкрити теку в Claude Code. Файл `CLAUDE.md` підхопиться сам. Першим повідомленням написати: «Моя роль — ____».
4. Створити свою гілку: `git switch -c <роль>/<що-роблю>`, наприклад `frontend/calendar-heatmap`.

## 3. Щоденний цикл роботи з кодом

1. Перед початком: `git switch main`, `git pull`, потім нова гілка від свіжого `main`.
2. Працювати **лише у своїй теці** (`pipeline/`, `model/`, `backend/`, `frontend/`, `docs/`). Так конфлікти майже не виникають.
3. Комітити часто, малими шматками, зі зрозумілим описом.
4. `git push`, відкрити Pull Request у `main`. В описі — що зроблено і як перевірити.
5. Мерджить капітан. Перед мерджем — сайт запускається і не зламаний.
6. Якщо гілка живе довше 3–4 годин — підтягнути `main` у неї (`git pull origin main`), щоб не накопичувати розбіжності.

**Заборонено:** комітити прямо в `main`; `git push --force` у спільні гілки; змінювати файли в чужій теці без слова її власникові.

Можна просити Claude Code: «закоміть мої зміни й відкрий Pull Request» — він зробить це правильними командами.

## 4. Як об'єднуються дані між ролями

Ланцюжок: **FIRMS → `grid_monthly` (світ) + `fires` (Україна) → `grid_harmonized` + `calendar` + `metrics` → файли для сайту → фронтенд.** Кожна ланка віддає наступній файл у форматі контракту з `CLAUDE.md` (версія 2). Формат контракту без згоди команди не міняється.

| Крок | Хто | Що віддає | Куди кладе |
|---|---|---|---|
| 1 | Data engineer | Сирі CSV із FIRMS (світ по роках, Україна) | Drive: `raw/` |
| 2 | Data engineer | `grid_monthly_vN.csv` (світ, клітинки 0,25°), `fires_vN.csv` (Україна) | Drive: `processed/` |
| 3 | Data scientist | `grid_harmonized.csv`, `calendar.csv`, `metrics.json` | Drive: `processed/`; малі файли — репозиторій `data/` |
| 4 | Капітан | JSON для сайту: `regions.json`, `grid/<tile>.json`, `calendar/<region_id>.json`, `fires/UA/<YYYY-MM>.json`, `metrics.json` | репозиторій: `frontend/public/data/` |
| 5 | Фронтенд | Сайт, що читає ці файли через `api.js` | репозиторій: `frontend/` |

Почніть ланцюжок на Україні: файли малі, усе проходить за хвилини. Коли працює від початку до кінця, той самий код запускається на світі.

Правила, які рятують від плутанини:
- **Фейкові дані з першої години.** Капітан одразу кладе у `frontend/public/data/` вигадані файли в точному форматі контракту. Фронтенд і дизайн працюють, не чекаючи справжніх даних. Потім файли просто замінюються.
- **Версії в назві.** `fires_v1.csv`, `fires_v2.csv` — старі не затираємо. У чаті пишемо: «виклав fires_v2, змінилось те-то».
- **Скрипт, а не ручна правка.** Кожен файл даних створюється скриптом із репозиторію (`pipeline/`, `model/`). Тоді будь-хто може відтворити результат, і це аргумент для критерію Validity.
- **Перевірка на вході.** Скрипт наступної ланки спершу перевіряє назви колонок і кількість рядків, а вже тоді рахує. Якщо формат не той — зупиняється з повідомленням.
- **Файл `data/README.md`**: для кожного файла — хто створив, яким скриптом, з якої версії вхідних даних, дата.
- **Ключі не в git.** `MAP_KEY` від FIRMS та інші секрети — у локальному файлі `.env`, який внесено до `.gitignore`. Репозиторій публічний.

## 5. Ритм синхронізації

- Кожні 4–6 годин — 10 хвилин усі разом: що зроблено, що далі, де застряг.
- Хто застряг довше ніж на 30 хвилин — пише в чат одразу, не чекає синхронізації. Дублери: Микола ↔ Єгор ↔ Іван (дані), Михайло ↔ Василина (інтерфейс), капітан ↔ Михайло (деплой).
- Після кожного мерджу в `main` капітан перевіряє живий сайт і пише в чат: «main оновлено, сайт працює».
- Фіча-фриз о 15:55 15.11: далі лише виправлення.

## 6. Робота з ШІ в команді

- У кожного свій Claude Code, але **один спільний `CLAUDE.md`**. Зміни в ньому — лише через Pull Request, щоб усі асистенти мали однаковий контекст.
- Домовленість, прийнята усно, записуємо в `CLAUDE.md` того ж дня. Інакше ШІ в різних учасників зробить по-різному.
- Просити ШІ писати малими кроками й запускати кожен крок. Не приймати великий шматок коду, який ніхто не запускав.
- Кожне нове використання ШІ — рядок у `docs/SI_USAGE_LOG.md`.

## 7. Якщо щось пішло не так

| Ситуація | Що робити |
|---|---|
| Конфлікт під час `git pull` | Не вгадувати. Показати Claude Code або капітанові; у чужих рядках лишати версію власника теки |
| Зламався `main` | Капітан відкочує останній мердж (`git revert`), автор виправляє у своїй гілці |
| Зник інтернет або GitHub | Працювати локально, комітити; файли даних передати через Drive або флешку |
| Хтось випав | Дублер бере його відкриту задачу з дошки; усе потрібне вже в репозиторії |
